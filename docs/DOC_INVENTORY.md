Every `.md` file in the repository appears exactly once below.

## The three fields

They are orthogonal, and conflating them is what produced the mess this register cleans up.

**Lifecycle** — one of four, and nothing else:

| Value | Meaning |
|---|---|
| `Current` | Describes present behaviour. Maintained with the code. May be cited as authority. |
| `Active plan` | Approved work not yet fully implemented. Needs an owner and exit criteria. |
| `Historical evidence` | Records what happened. Never normative. Points forward to the current contract. |
| `Archived` | Useful implementation history, no longer maintained. Names its replacement. |

**Authority** — *optional*. Only documents that are the single canonical source for a topic
declare it. Explanatory, rationale, and historical documents legitimately have none, and forcing
them to claim one invents authority that does not exist.

**Provenance** — `hand-written` or `generated by <command>`. Independent of lifecycle: a
generated file can be current, historical, or archived. Generated files are exempt from the
lifecycle-banner requirement (PR4 check 4) because the generator, not a human, owns their text.

## Rules this register enforces

1. A `Current` document may not take a `Historical evidence` or `Archived` document as its
   **normative source**. Citing one for rationale or provenance is fine and common — the
   distinction is whether removing the citation would leave a claim unsupported.
2. Campaign records are evidence, not contract (`DECISIONS.md` D3).
3. A handoff is temporary. Once its receiving work starts it converts to an active plan, folds
   into a canonical reference, or archives. `docs/handoffs/` is not a queue.
4. An execution plan leaves the active tree when its work lands.
5. `Active plan` requires an owner and exit criteria; without them it is not a plan.
