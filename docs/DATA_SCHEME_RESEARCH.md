# Designing a Future-Compatible Data Schema and Parser Architecture for Inelastic Scattering Reduction (ISAR)

## TL;DR
- **Adopt a "generalized scan axis" model now**: represent every scan as N measured points × M *named, typed* scan columns (any combination of energy, H/K/L, |Q|, an angle, or a sample-environment variable) plus a measured-signal block (counts + error) and a per-point environment/log table. NeXus's `NXtas` and the SPICE "everything-is-a-motor" model both validate this; constant-Q-vs-energy is just the special case M=1, axis=energy.
- **Build five extension points from the start**: (1) a list-of-scan-axes instead of a hardcoded energy axis; (2) a typed-but-open sample-environment/log container (key→series, with units, setpoint, sensor id, validity mask); (3) a normalization block carrying BOTH monitor counts and counting time plus the counting mode; (4) a multi-spectrum signal block (one scan → many spectra, as on HERIX's nine analyzers); and (5) a per-facility, per-version parser registry that detects format and dispatches. These cover the realistic future cases (polarized INS, multi-analyzer, operando, pump-probe) without a schema rewrite.
- **Don't over-build**: full N-dimensional MD/event data (Mantid MDWorkspace / Horace SQW), live event streaming, and a universal 3D instrument-geometry model are NOT needed for during-beamtime triage of step-scanned 1D spectra. Keep signal/axes as arrays and keep provenance so they *could* be added, but defer them.

## Key Findings

**1. A community-blessed abstraction for the TAS/IXS scan already exists, and ISAR should mirror it.** The NeXus `NXtas` application definition stores every quantity that can vary during a scan as a parallel array of length `nP` (number of points): `qh[nP]`, `qk[nP]`, `ql[nP]`, monochromator `ei[nP]`, analyser `ef[nP]`, monochromator/analyzer `rotation_angle[nP]`, `polar_angle[nP]`, and detector `data[nP]`. NXtas is explicitly "for the trademark scan of the TAS, the Q-E scan," and defers alignment scans to the generic `NXscan`; its `probe` field accepts `neutron | x-ray`, so IXS reuses it. ORNL's SPICE control system (HB-1/HB-3) generalizes further: "all changeable quantities (including physical motors, pseudomotors, sample environment quantities, flipper voltages, etc.) are all treated as motors," and its `scanon` structure "allows any combination of drives and counts to be converted into a properly formatted scan." The 2002 NeXus inelastic proposal (Beckmann et al., built from PANDA/PUMA at FRM-II) makes the rule explicit: "store all parameters which might change during a scan in arrays… The scanvariable array in the first NXdata group therefore holds ki values while the scanvariable array of the second NXdata group holds temperature values. It is the task of the data processing software to keep track on that." This "list of scanned columns + measured signal" pattern is the single most important borrowable idea.

**2. The XYE layout the user needs is the universal lowest common denominator — but X must be a named, typed axis.** Mantid's `MatrixWorkspace` is fundamentally X (axis, e.g. energy or H), Y (counts/signal), E (error) per spectrum. ESRF ID28's reduction tool `addIXS` outputs precisely "an xye file, where x is the energy transferred to the sample, y is the normalized intensity (normalized to monitor 'ione'), e is the square-root error on the intensity." SPEC files (APS Sector 30, legacy ID28) are column ASCII in which "the first column is always the primary scanned item" and the trailing columns are monitor/counter. So an XYE-with-named-X core is correct — but X must be a *named, typed* axis (energy | H | K | L | |Q| | angle | temperature | field), never implicitly energy.

**3. Per-scan normalization must carry both monitor AND time, plus the counting mode.** TAS/IXS instruments count in one of two modes: fixed-monitor (count until a beam monitor reaches a preset number) or fixed-time (count a preset number of seconds). SPEC encodes this directly: "the second to last column is the counter assigned to MON when counting to time. When counting to monitor the second to last column is the counter sec." Both quantities are therefore always in the file, and which one is the fixed preset flips with the mode. The monitor — a low-efficiency beam monitor sampling incident flux — is the physically correct flux normalizer. For combining runs, Mantid's MDNorm documentation gives the error-safe rule: "we should not normalize data by monitor counts and then add different experiments together… We should instead add raw data together, add monitors together, and only then divide." Errors are Poisson (σ = √N on raw counts) propagated through the division. ISAR's normalization block must store: `counting_mode` (monitor|time), `monitor[nP]`, `time[nP]`, the preset value, and a monitor-correction flag (thermal-TAS monitors have a known λ/2 contamination that is routinely subtracted — e.g. published HB-1 data are "corrected for contamination of the incident beam monitor").

**4. The energy axis is absolute on a fixed-kf TAS but must be derived/calibrated on IXS.** On a triple-axis spectrometer the energy transfer is computed deterministically from ki and kf, and fixed-kf (or fixed-ki) operation makes the absolute energy axis known from the instrument configuration (e.g. HB-3 phonon work at fixed Ef = 14.7 meV "varying the incident neutron energy in constant Q mode"; IN8 at fixed kf = 2.662 Å⁻¹). The schema must therefore record geometry: fixed-ki vs fixed-kf, the fixed k (or E) value, monochromator and analyzer crystal+reflection (PG(002), Si(111), Cu, Heusler for polarized), collimations (e.g. 48'-40'-40'-120'), and filter. On meV-IXS the situation is fundamentally different: energy is scanned by varying the **monochromator temperature** — exploiting the thermal expansion of the Si backscattering crystal, "approximately 17 mK/meV near RT at 21.7 keV, as calibrated by a known phonon line" (Baron group, arXiv:2103.04002) — and the file stores **temperature as the abscissa, not energy**. The energy axis is then derived from temperature, and the **energy zero must be calibrated from the elastic line** (the quasi-elastic peak position), since the absolute zero is not known a priori; the same source notes scans run in both directions "coincide to better than 0.02 meV." ID28's addIXS "uses the Si reflection order… to convert the temperature of the monochromator into the energy." ISAR's schema must therefore support a "raw abscissa → calibrated energy" transform with a fitted elastic-line zero offset as first-class metadata, not a hardcoded energy column.

**5. NeXus provides a typed-but-extensible sample-environment model — borrow its structure.** `NXsample` carries `temperature` ("This could be a scanned variable"), `magnetic_field`, `electric_field` (NX_VOLTAGE), plus pressure/stress/strain fields, each an array whose length equals the number of values in that field (`n_eField`, `n_mField`, `n_pField`, `n_sField`). For richer cases NeXus uses `NXenvironment` ("Any environmental or external stimuli/measurements… applied pressure, surrounding gas phase and gas pressure, external electric/magnetic/mechanical fields, temperature") containing `NXsensor` groups. `NXsensor` has an enumerated-but-open `measurement` type (temperature | pH | magnetic_field | electric_field | current | conductivity | resistance | voltage | pressure | flow | stress | strain | shear | surface_pressure, "or a custom value"), plus `value` (setpoint/average), `value_deriv1`, and `run_control` ("Is data collection controlled or synchronised to this quantity"). For time-series logging NeXus uses `NXlog` (value + time arrays); the streaming rule is "just use the standard NeXus raw data file structure, but replace the corresponding data object with an NXlog." Mantid implements the pragmatic version as **sample logs**: arbitrary key→(time-series) values on the workspace `Run` object, accessible via `getLogData()`, addable via `addProperty('sample.pressure', 23., …)`, "from magnetic fields to temperatures." Mantid also natively handles the disconnected/unreliable-sensor case: `SampleLogsModel.get_logs_with_invalid_data()` flags fully/partially invalid logs and stores `_invalid_values` masks. This is the model ISAR should copy.

**6. Native file formats per instrument — and they drift.**
- **APS Sector 30 HERIX (IXS):** SPEC ASCII files; instrument logic lives in SPEC `.mac` macros (the APS temperature macro at `subversion.xray.aps.anl.gov/spec/common/bcda/temperature.mac` reads EPICS setpoints/sensors and carries edits dated 2004–2012). HERIX has **nine analyzers with an angular (momentum) separation of 0.95° (2 nm⁻¹) between adjacent analyzers**, resolving power ΔE/E ≃ 6 × 10⁻⁸ at 23.724 keV, Qmax = 72 nm⁻¹ (Said et al., *J. Synchrotron Rad.* 27, 827–835, 2020) — so one scan yields nine spectra at nine Q values simultaneously. Sample environment includes a Razorbill uniaxial-strain cell ("maximum applicable strain displacement is 12 µm (±6 µm) at room temperature and half of the range at 10 K… measured by capacitance"), static magnetic fields and high pressure, over 5–1000 K.
- **ESRF ID28 (IXS):** Native raw format is **ASCII SPEC files**; the nine analyzer signals are separate per-detector columns in one scan, and addIXS emits one file per analyzer named `<spec>_<scan>_A<det>.dat`. Energy is stored as **monochromator temperature**, monitor is "ione," and each analyzer needs its own temperature offset because the analyzer thermistors read very different temperatures "due to the different contact resistances on the thermistors." Per-analyzer resolution differs slightly: "3 meV on average, with small variations (<10%)… 2.96(7) meV for analyzer 2 of ID28, from the fit of the elastic line width" (arXiv:2203.15311). ESRF-wide, the BLISS control system writes NeXus/HDF5 under the ESRF data policy, but **no public document confirms ID28's IXS spectrometer has migrated**; a 2024 review still lists ID28 among beamlines awaiting major refurbishment, so SPEC ASCII should be assumed for current and legacy ID28 data.
- **SPring-8 BL43LXU (IXS):** Uses **custom in-house acquisition software** (Baron's Materials Dynamics Laboratory); the on-disk format (ASCII vs binary) is **not publicly documented** in Baron's review papers or SPring-8 docs — treat this as a "confirm-with-staff" parser developed against real sample files. Its analyzer count is a large 2D array: the RIKEN page describes a 6×4 array (now 28 analyzers), and a 2024 experiment used "a two-dimensional array of 7 × 4 = 28 analyzers… to collect data from 28 different momentum transfers in each scan" (arXiv:2510.19790), with resolution between ~0.75 and 6 meV.
- **ILL IN8 (TAS):** ILL "numor" format (NUMber Of Run; 6-digit zero-padded filenames), historically ASCII/TAPDAT-derived. ILL provides LAMP (IDL), Paul Steffens' MATLAB TAS routines, and the Rplot tool, which opens numors of "any type of scan." Newer ILL instruments emit NeXus/HDF5 (IN5; D17 from January 2023), but TAS data has remained in the classic numor lineage. The format still drifts (Rplot notes: "adapted to new D3 Numor format"). IN8 itself was rebuilt (new "ThermES" secondary spectrometer) and runs either as a single-detector instrument or in IMPS multi-analyzer mode (nine (Q,ω) points simultaneously via a nine-blade Ge(111) analyzer + PSD).
- **HFIR HB-3 (TAS):** ORNL **SPICE** format — column ASCII with a structured header, written by the LabVIEW-based SPICE control system (also used on HB-1). SPICE uses a UB-matrix formalism generalized for inelastic scans and treats all environment quantities as motors. The modern ORNL reader/reducer is **TAVI** (Triple Axis data Visualization Toolkit, `github.com/neutrons/TAVI`, actively developed through 2026), which works with SPICE data and an HDF5 representation.

**7. The standards landscape, assessed for borrowability:**
- **NeXus** (`NXtas`, `NXspe`, `NXsample`, `NXenvironment`, `NXsensor`, `NXlog`, `NXdata`, generic `NXscan`): the richest, most directly mappable model. `NXtas` is the canonical Q-E scan; `NXspe` (used by Mantid/Horace) is for reduced direct-geometry S(Q,E). There is **no `NXinelastic`/`NXixs`** application definition — IXS reuses `NXtas` with `probe="x-ray"`. NeXus is the recommended *vocabulary* target for ISAR's normalized schema even if ISAR keeps an in-memory Python object.
- **Mantid**: `MatrixWorkspace` (XYE + spectra), `MDWorkspace` (N-dim event/binned for mapping, with `CreateMD`/`BinMD`/`CutMD` in the Q3D/HKL frame), sample logs (arbitrary metadata), the `Run` object, and versioned instrument definition files (IDF, XML). The gold standard for the signal+logs+history triad and for backward compatibility.
- **TAS analysis ecosystem**: Takin (open-source; Eckold-Sobolev plus Cooper-Nathans/Popovici resolution; convolution fitting), ResLib/ResLibCal (MATLAB; Cooper-Nathans/Popovici), and Python ports NeutronPy, Inspy/TasVisAn, and `scattering/rescalculator`. These are resolution/convolution engines ISAR's later DHO-convolution phase can call rather than reimplement; they consume the (Q,E) point + instrument config the schema must already carry.
- **DAVE/MSlice** (NIST): mature low-energy INS reduction/visualization (DCS, HFBS, FANS, TAS, NSE) but TOF-centric and IDL-based — less relevant as a schema source than NeXus/Mantid.
- **SciCat / PaN (ExPaNDS, PaNOSC, PaNET ontology)**: SciCat is a NoSQL metadata *catalogue* for FAIR findability, built to "accommodate heterogeneous data" (structured + free-form) — not a scan data model. Relevant to ISAR only if it later pushes metadata to a facility catalogue; the PaNET ontology offers controlled technique vocabulary. Not a normalized scan model to map onto.

**8. Parser/schema versioning best practice exists in Mantid and is directly transferable.** Mantid resolves which instrument geometry to apply by a **valid-from date** embedded in versioned IDF files (`INSTRUMENTNAME_DefinitionANYTHING.xml`); if a file embeds its own definition that is used, otherwise Mantid matches by date — which requires the data file to "contain a record of when the data were collected." NeXus achieves forward/backward compatibility via its self-describing hierarchy, the `NeXus_version` attribute, and additive application definitions (new optional fields don't break old readers). Transferable pattern: detect (facility, instrument, format-version) from file content/headers/date, dispatch to a parser registered on that tuple, and stamp every normalized scan with the parser version and source format for provenance.

## Details

### The generalized scan-axis abstraction (point 1)
The normalized scan object should be, concretely:
- `scan_axes`: an ordered list of axis descriptors, each `{name, role, units, values[nP], kind}` where `kind ∈ {energy, q_component(H|K|L), q_modulus, angle(A3|A4|A2|mono|ana), environment(temperature|field|…)}` and `role ∈ {scanned, derived, constant}`. A constant-Q energy scan has one scanned axis (energy) with Q recorded as constant axes; a constant-E Q-scan along H has one scanned axis (H); a rocking curve has one scanned angle; a T-ramp has one scanned environment axis; a mesh/map has ≥2 scanned axes — the same container handles all of them.
- `signal`: `{value[nP, n_spectra], error[nP, n_spectra], spectrum_coords}` where `n_spectra = 1` for a single-detector TAS, `9` for HERIX/ID28, `28` for a BL43LXU array, `9` for IN8-IMPS, with `spectrum_coords` giving each spectrum's Q-offset/analyzer angle.
- Keeping the scanned variable as *one element of a list* rather than a privileged "energy" field — as NXtas, the Beckmann proposal, and SPICE all do — is what prevents a rewrite when the user later runs a constant-E scan or a field ramp.

### Required per-scan metadata (point 2)
Minimum viable record: `counting_mode`, `monitor[nP]`, `time[nP]`, `preset`; `temperature` as `{setpoint[nP], sensors:{name→value[nP]}, valid_mask}` (multiple sensors, disconnected-sensor failure handled by the mask, as Mantid does); geometry `{fixed_mode: ki|kf, fixed_value, mono:{crystal,reflection}, ana:{crystal,reflection}, collimation[4], filter, focusing}`; and for IXS an `energy_calibration` block `{raw_abscissa_kind: temperature|angle, transform, elastic_zero_offset, resolution_fwhm}`. The fixed-kf-absolute vs IXS-elastic-line-calibrated distinction must be a flag, because it determines whether the energy axis can be trusted as loaded or must be fitted.

### Extensible sample environment (point 3)
Recommended container: a **hybrid**. Promote the two common variables (temperature, magnetic_field) to typed fields with sensor/setpoint substructure (reduction logic and QC reference them directly), and back everything else with an **open `logs` dictionary** keyed by name, each entry `{values[nP] or time-series, units, setpoint, sensor_id, role(scanned|monitored|constant), valid_mask}`. This is Mantid sample logs + NeXus `NXsensor` typing. Custom electric field, uniaxial/hydrostatic pressure, strain (the HERIX Razorbill cell, ±6 µm at room temperature), laser illumination, and gas loading all drop into `logs` with no schema change, and any of them can be promoted to a scanned axis by reference from `scan_axes`.

### Forward-compatibility — the principal axes of variation (point 7)
1. **Dimensionality of the scan** (1 → N scanned axes): handled by the `scan_axes` list.
2. **Identity of the scanned variable** (energy | Q-component | angle | environment): handled by axis `kind`.
3. **Number of spectra per scan point** (1 → many): HERIX 9, ID28 9, BL43LXU 28, IN8-IMPS 9 — handled by the `n_spectra` dimension + `spectrum_coords`. **Build now**; it is already required by the user's named instruments.
4. **Polarization/spin channels** (polarized INS, Heusler mono/analyzer, XYZ or spherical polarimetry as on HB-1, the polarized sister of HB-3): model as a `channel` coordinate `{spin_in, spin_out, flipper_state}` on the signal block. Reserve the dimension now (length-1); populate later.
5. **Energy-axis provenance** (absolute TAS vs elastic-calibrated IXS): the flag above.
6. **Independent variable being an environment ramp** (T or B ramp): already covered by `kind=environment`.
7. **Time/pump-probe** (delay as an axis): drops in as another axis `kind` + a `delay` log; defer implementation, don't preclude it.
8. **Multi-sample/sample-array**: an optional `sample_id` coordinate; defer.

## Recommendations

**Build into v1 (non-negotiable — the user's five instruments already require them):**
1. **Generalized `scan_axes` list** (named, typed, role-tagged) instead of a hardcoded energy column. Low cost, and it carries the entire forward-compatibility story.
2. **Multi-spectrum signal block** (`value[nP, n_spectra]`, `error`, `spectrum_coords`). HERIX (9), ID28 (9), BL43LXU (28), IN8-IMPS (9) all produce many spectra per scan; a single-spectrum schema would need a rewrite on day one.
3. **Normalization block with both monitor and time + `counting_mode`**, combine-before-divide semantics for future run-merging, and Poisson √N error propagation from raw counts.
4. **Hybrid environment container**: typed temperature + magnetic_field (multi-sensor, setpoint, validity mask) plus an open `logs` dict for arbitrary parameters. Mirrors Mantid sample logs + NeXus NXsensor.
5. **IXS energy-calibration block** (raw abscissa kind, T→E transform, elastic-line zero offset, resolution FWHM) and a fixed-ki/kf geometry block for TAS. Without this the energy axis is wrong for IXS.
6. **Parser registry keyed on (facility, instrument, format_version)** with content/date-based detection and per-scan provenance stamping (source format, parser version, normalized-schema version). Adopt Mantid's valid-from-date dispatch idea.
7. **Map field names onto NeXus vocabulary** (NXtas/NXsample/NXsensor terms) even in the in-memory object, so a future NeXus export or SciCat push is mechanical.

**Defer (design so they slot in; don't implement):**
- Polarization/spin-channel dimension — reserve the coordinate, leave it length-1.
- Pump-probe delay axis and multi-sample id — additional axis kinds / coordinates.
- Full N-dimensional MD/event representation (Mantid MDWorkspace, Horace SQW) and live event streaming — overkill for during-beamtime triage of step-scanned 1D spectra; revisit only if ISAR expands to TOF or large-scale multiplexing mapping.
- A full constructive-solid-geometry instrument model (Mantid IDF) — ISAR needs scalar geometry parameters (fixed k, crystals, collimations) for resolution, not 3D detector geometry.

**Benchmarks that would change these recommendations:** routine mesh/map scans → promote multi-axis handling and consider a thin MD layer; polarized HB-1 data entering the pipeline → activate the spin-channel dimension; a facility format migration (ID28 → BLISS/HDF5, or ORNL TAS → TAVI HDF5) → add a new parser keyed to the new (instrument, version) tuple without touching the normalized schema.

## Caveats
- **BL43LXU's native file format is not publicly documented**; Baron's review papers describe optics and physics but not the on-disk acquisition format. ISAR's BL43LXU parser should be developed against real sample files and confirmed with beamline staff, not built from a spec.
- **ID28's migration status to BLISS/HDF5 is unconfirmed in public sources**; assume SPEC ASCII for current and legacy data, but design the parser registry so an HDF5 ID28 variant can be added.
- **Format drift is real and continuous**: ILL numor format has versioned changes (Rplot: "adapted to new D3 Numor format"); APS SPEC macros show edits spanning 2004–2012; IN8 was rebuilt (ThermES), changing its configuration. Several-year-old user data may predate current conventions — hence the per-version parser registry is essential, not optional.
- **`NXtas` is a thin application definition** (it standardizes the Q-E scan arrays, not the full breadth of environment/polarization); treat it as a vocabulary anchor and supplement with NXsample/NXenvironment/NXsensor/NXlog.
- **Monitor normalization carries instrument-specific corrections** (thermal-TAS λ/2 monitor contamination is routinely subtracted); store a monitor-correction flag rather than assume the monitor column is clean.
- **Resolution must be stored per spectrum, not per scan**: for multi-analyzer IXS each analyzer has a slightly different resolution (ID28: 2.96(7) meV for analyzer 2 vs ~3 meV average), which matters for the later DHO-convolution fitting phase.
